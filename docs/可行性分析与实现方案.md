# Electron + Node.js 内嵌浏览器 & 磁力识别工具 — 可行性分析与实现方案

> 适用场景：桌面端内嵌一个简易浏览器，访问指定网址，对网页做二次加工（去广告、删栏目、识别磁力链接、悬浮预览）。
> 本文给出可行性结论、技术选型、整体架构与关键模块设计，并配套一份可直接运行的 Electron 骨架（`magnet-browser/`）。

---

## 一、可行性结论

**结论：完全可行，技术风险低。** 四项需求均有成熟、可落地的解法，核心难点（页面注入、跨进程通信）在 Electron 里都是一等公民能力。

| 需求 | 落地技术 | 难度 | 主要风险点 |
|---|---|---|---|
| 内嵌简易浏览器访问指定网址 | `<webview>` 标签 / `WebContentsView` | 低 | 新版 Electron API 变动 |
| 移除广告栏 | `insertCSS` 隐藏 + `executeJavaScript` 删除节点 | 低 | 动态插入广告、跨域 iframe 内广告 |
| 隐藏/删除指定栏目 | 配置化 CSS 选择器 + DOM 移除 | 低 | 目标站点改版导致选择器失效 |
| 自动识别磁力链接 | 正则扫描 + `MutationObserver` 监听动态内容 | 低 | 纯文本型磁力、编码混淆 |
| 悬浮预览窗口 | 页内 overlay div（推荐）/ 独立透明 `BrowserWindow` | 中 | 独立窗口方案需做屏幕坐标映射 |

**为什么「页面注入」一定能成功**：我们的 CSS/JS 注入走的是浏览器引擎层（`insertCSS` / `executeJavaScript` 由宿主进程下发），不是页面自己的脚本，因此**不受目标站点 CSP（内容安全策略）限制**。这是该项目可行性的关键支撑点。

## 二、技术路线选型

### 2.1 内嵌网页的三种方案

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| `<webview>` 标签 | 作为 DOM 元素，布局简单，自带 `preload`/`insertCSS`/`executeJavaScript` | 官方标记「偏 legacy」，部分新特性滞后 | **骨架采用**，最易上手 |
| `WebContentsView`（Electron ≥30，取代 `BrowserView`） | 官方现行方案，性能好，可多视图 | 需手动布局，不带 DOM 容器 | 追求新 API 时采用 |
| `<iframe>` | 零依赖 | 无法注入脚本、无法跨域操控、受 CSP 限制 | ❌ 不满足二次加工需求 |

### 2.2 内容注入的三层通道

1. **CSS 注入（`insertCSS`）** — 隐藏类需求首选（广告栏、栏目隐藏），不破坏页面原有 JS 逻辑。
2. **JS 注入（`executeJavaScript`）** — 节点删除、读取 DOM、调用页面函数。
3. **Preload 脚本** — 常驻页内，负责动态内容的实时监听与跨进程通信（`ipcRenderer.sendToHost`）。

> 关键认知：能 CSS 隐藏的就不要 JS 删除（更稳）；必须删除的（如移除某个交互栏目）再用 JS 移除节点。

### 2.3 进程模型

```
主进程 (main.js)         ── 创建窗口、读 rules.json、IPC 桥接、DHT(可选)
   │
   ├─ 渲染进程 (index.html + renderer.js)  ── 工具栏 UI、规则下发、磁力计数
   │      │
   │      └─ <webview> 宿主页
   │             │
   │             └─ 访客预加载 (preload.js)  ── 注入页内：磁力扫描 + 悬浮 overlay + 栏目删除
```

## 三、整体架构

### 3.1 模块划分

| 模块 | 职责 | 所在进程 |
|---|---|---|
| 浏览器内核模块 | 加载指定网址、前进/后退、导航拦截、新窗口管控 | 主进程 + 渲染进程 |
| 内容过滤模块 | 按规则隐藏/删除广告与指定栏目（CSS + DOM） | 访客预加载 |
| 磁力识别模块 | 正则扫描 `<a href="magnet:">` 与纯文本磁力串，去重上报 | 访客预加载 |
| 悬浮预览模块 | 鼠标悬停磁力链接时显示信息卡片 | 访客预加载（页内 overlay） |
| 规则配置模块 | 读取 `filter-rules.json`，支持按域名定制 | 主进程（fs）+ 下发渲染进程 |
| 元数据解析（演进） | 通过 DHT 解析磁力对应的文件名/大小列表 | 主进程（Node 子进程/库） |

### 3.2 目录结构（骨架）

```
magnet-browser/
├─ package.json            # electron 依赖与启动脚本
├─ main.js                # 主进程：建窗、读规则、IPC
├─ preload-main.js        # 窗口自身 preload（contextBridge 暴露 API）
├─ index.html             # 工具栏 + <webview> 容器
├─ renderer.js            # 工具栏逻辑、规则下发、磁力计数
├─ preload.js             # 访客预加载：磁力识别 + overlay + 栏目删除
└─ config/
   └─ filter-rules.json   # 过滤规则（CSS 隐藏 / DOM 删除选择器）
```

## 四、关键模块设计

### 4.1 浏览器内核模块
- 用 `<webview>` 承载目标站，`src` 设为指定网址。
- 拦截 `new-window` / 弹窗，强制在同视图内打开，避免「逃逸」到系统浏览器。
- 导航事件（`did-navigate`）回写地址栏；支持前进/后退。

### 4.2 内容过滤模块（配置驱动）
规则文件 `filter-rules.json`：
```json
{
  "cssHide": ["#top-ad", ".ad-banner", "[data-ad]"],
  "removeSelectors": [".sidebar", "#recommend-column"]
}
```
- `cssHide` → 主进程/渲染进程调用 `webview.insertCSS(selector + "{display:none!important;}")`。
- `removeSelectors` → 下发到访客页，由 `preload.js` 的 `applySiteFilters()` 执行 `el.remove()`。

### 4.3 磁力识别模块
- 正则：`/magnet:\?xt=urn:btih:([a-z0-9]{32,40})/i`。
- 两类来源：① `<a href="magnet:...">` 显式链接；② 正文纯文本中的磁力串（用 `TreeWalker` 扫文本节点，命中后包成 `<a>`）。
- 用 `MutationObserver` 监听 DOM 变化，覆盖 SPA / 异步加载的内容（回调内先 `disconnect` 再扫描再 `observe`，避免自触发死循环）。
- 命中后 `ipcRenderer.sendToHost('magnet-detected', info)` 上报主/渲染进程（可用于去重、本地落库、计数）。

### 4.4 悬浮预览模块
- **推荐方案：页内 overlay div**。`preload.js` 注入一个 `position:fixed; z-index:2147483647` 的信息卡，监听磁力链接的 `mouseenter/mousemove/mouseleave` 显示/跟随/隐藏。
- 展示内容：解析出的 `dn`（名称）、`btih` hash 前若干位、`tr`（Tracker 数量）、`xl`（大小）。
- **进阶方案（更「窗口感」）**：另建一个 `BrowserWindow`（`frame:false`、`transparent:true`、`alwaysOnTop:true`），用链接的 `getBoundingClientRect()` + 主窗口屏幕坐标定位，悬停时显示。代价是跨窗口坐标映射，略复杂。

### 4.5 规则配置模块（Node.js 角色）
- 主进程用 `fs` 读取 `filter-rules.json`，经 IPC 下发渲染进程，再注入 `<webview>`。
- 支持按域名定制规则（key 为域名，value 为上面的规则对象），命中当前站点才应用。
- 可扩展：规则热更新（文件监听 `fs.watch`）、用户可视化编辑界面。

### 4.6 演进：DHT 元数据解析（对接你的「磁力搜索引擎」方向）
仅靠磁力串只能拿到 hash 与 `dn`。要获取**真实文件列表/大小**，需连 DHT 网络解析 `ut_metadata`。Node 侧可用 `bittorrent-dht` / `magnetite` 等库，在**主进程子进程**里跑（不阻塞 UI），解析结果回填到悬浮预览。这正好是你远期「DHT 磁力链接搜索引擎」的能力底座。

## 五、核心代码要点（完整见骨架）

访客预加载里的磁力扫描与悬浮（`preload.js` 核心逻辑）：
```js
// 正则 + 文本节点扫描 + 悬停 overlay
const MAGNET_RE = /magnet:\?xt=urn:btih:([a-z0-9]{32,40})/i;

function scan() {
  document.querySelectorAll('a[href^="magnet:"]').forEach(a => bindLink(a, parseMagnet(a.href)));
  const walker = document.createTreeWalker(document.body, NodeFilter.SHOW_TEXT, {
    acceptNode: n => (/^magnet:/i.test((n.nodeValue||'').trim())) ? NodeFilter.FILTER_ACCEPT : NodeFilter.FILTER_SKIP
  });
  let t; const texts = []; while ((t = walker.nextNode())) texts.push(t);
  texts.forEach(node => { /* 包成 <a> 并 bindLink */ });
}

const observer = new MutationObserver(() => {           // 覆盖动态加载
  observer.disconnect(); try { scan(); } finally { observer.observe(document.documentElement, {childList:true, subtree:true}); }
});
```

## 六、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 目标站改版 | 选择器失效，广告/栏目重新出现 | 规则外置为 JSON，支持热更新与按域名定制；提供「一键反馈失效」入口 |
| 跨域 iframe 内广告 | `insertCSS`/`executeJavaScript` 默认只作用于顶层 | 遍历 `webview.getWebContents().getAllFrames()`，逐帧注入 |
| 文本型磁力编码混淆 | 链接被拆段 / Unicode 混淆 | 先归一化文本（去空白、解码）再匹配；正则放宽 |
| 悬浮 overlay 被站点 `z-index` 盖住 | 极端情况下 | 用 `2147483647` 最大层级 + `!important`，必要时独立窗口方案 |
| 注入影响页面功能 | JS 删节点可能误伤 | 优先 CSS 隐藏；删除类选择器仅用于明确无交互依赖的栏目；加白名单 |
| Electron 版本碎片化 | `BrowserView`/`WebContentsView` API 变动 | 骨架用 `<webview>`（跨版本稳定）；升级时再切 `WebContentsView` |

## 七、落地里程碑

1. **M0 骨架**：`<webview>` + 工具栏跑通，能加载指定网址（已完成于骨架）。
2. **M1 过滤**：接入 `filter-rules.json`，CSS 隐藏 + DOM 删除；验证动态广告（MutationObserver）。
3. **M2 磁力 + 悬浮**：正则扫描、`MutationObserver`、页内 overlay 预览；渲染进程计数器。
4. **M3 规则中心**：按域名定制、可视化编辑、热更新。
5. **M4 DHT 元数据**：主进程子进程解析文件列表/大小，回填预览（接入磁力搜索方向）。
6. **M5 打磨**：跨域 iframe 注入、性能（去重/节流）、打包（`electron-builder`）。

---

## 八、Node.js 在本项目里的真实价值
- `fs` 读取/热更新过滤规则；
- `better-sqlite3` 等本地库做磁力去重与历史库；
- 子进程跑 DHT 解析、避免阻塞渲染；
- IPC 桥接宿主与访客页，承担「配置中心 + 数据中转」角色。
- 纯前端方案做不了规则热更、本地库、DHT 网络，这正是「Electron 结合 Node.js」的必要性所在。
